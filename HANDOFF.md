## What the app is

One job: **a HubSpot contact list goes in, a worked call list comes out.**

1. Antonio picks a HubSpot contact list, a daily call target (default 50), and
   the day and start time of the calls.
2. `/generate` walks the list, applies filters, and asks one Octave agent for
   call intel, a voicemail script, a live call script, and objection handling
   per contact. It stops at the target.

   The filters, in the order they run: left the company, not a US number,
   already a customer, already prepped, called too recently, account already
   covered. The first two are free, because both read the contact record. The
   rest cost HubSpot requests.
3. He reviews, then presses START THE CLIMB, which writes a prep note onto each
   HubSpot contact record. **`/generate` writes nothing to HubSpot.** Only the
   approve step does.
4. On **Today's Climb** the BDR (Theresa) works the list, logs each outcome, and
   the card ticks off. The outcome becomes a HubSpot note. `do_not_call` also
   sets the standard `donotcall` property.

Two views: **Route Plan** builds the list, **Today's Climb** works it.

## Traps that already cost time

Read these before you debug anything. Each one cost a real detour.

**1. `/generate` writes nothing.** If someone says "the notes are not on the
contact", the usual cause is that START THE CLIMB was never pressed, not a
broken write. Check the server log for `POST /approve`. There is now a banner on
load that offers any unwritten plan back, because the write step used to be
unreachable after a reload.

**2. The Octave agent has a second, hidden set of instructions.** The agent
`ca_DLoI5XBlw9qGNEDBiV1a2` has `data.tools.crmActivity.customInstructions`,
which silently overrides the main prompt. Editing only `data.instructions`
changes nothing. The reviewable copy of the prompt is
`docs/octave-agent-instructions.md`; the live copy is in Octave and is the one
that runs. Read and write it with:

```
GET  https://app.octavehq.com/api/v2/agents/get?oId=<oid>     header: api_key
POST https://app.octavehq.com/api/v2/agents/update            body: {oId, data:{...}}
```

Partial updates work. `examples` is a list of strings.

**3. HubSpot lists are not all contact lists.** `objectTypeId` `0-1` is contacts,
`0-2` companies, `0-3` deals. A company list resolves to zero contacts and used
to produce a silent empty route. `/api/lists` now filters to `0-1`.

**4. No `oracle_*` custom property exists in this portal.** All nine are absent.
Anything that reads or writes them returns 400. That is why completion state
lives in the session file, not the CRM. `donotcall` did not exist either; it was
created on 2026-08-10 and is now written on `do_not_call`.

The `octave_*` properties are a different family and they do exist. Coverage is
thin and uneven, so check before depending on one. Measured on a 189-contact
list: `octave_qualify_reasoning` 0 of 189, `octave_qualify_verdict` 30,
`octave_segment` 30, `octave_geo_bucket` 30. The qualification prose the BDR
likes is not in HubSpot at all; an n8n workflow posts it to Slack. That is why
the call intel is generated by the agent instead of read from the CRM.

**4b. `state` is not a state and `country` is not a country.** In this portal
`state` holds LinkedIn style location strings, populated 189 of 189, for example
`New York, New York, United States` and `San Francisco Bay Area`. `country` is
populated 2 of 189 and holds full addresses. Do not substring match a country
name against them: `INDIANAPOLIS` contains `india`, which falsely flagged three
US contacts as Indian. `services/filters.py` checks US markers first and uses
word boundaries.

**5. `hs_timestamp` comes back as ISO on some endpoints and epoch millis on
others.** A raw string compare across the two silently never matches. See
`HubSpotClient._call_date`.

**6. Call pacing counts Antonio's calendar days, not UTC.** `services/timezone.
work_day` and `tzdata` in requirements.txt both matter. Without `tzdata` the
zone silently falls back to UTC on Linux only, and the cooldown misfires near
local midnight.

**7. Do not run two agent sessions against this working tree.** It happened on
2026-08-10 and one session swept the other's uncommitted files into its commit.
Check `git log` and `ps aux | grep claude` before assuming a change is yours.

**8. A dead SSE stream looks exactly like a slow one.** If a stream generator
raises, the response body just closes. The browser reads that as a clean end of
stream, so the page keeps the progress bar up and says nothing, while the
traceback sits only in the Railway log. `/quick-generate` did this on every run
that found a prep note: a stray `resolved` check copied from `/generate`
referenced a counter that did not exist there. Two guards now exist and both
must stay. `sse_response()` in `app.py` turns any escaping exception into an
`error` event. `reportUnfinishedStream()` in `index.html` reports a stream that
ends with no `complete`, `error`, or `done`. **If you add an SSE route, wrap it
in `sse_response`.** Check the Railway log for `Error handling request` before
you believe a report of a hang.

**9. The Octave output format changes shape between runs, on the same list.**
This is the single biggest source of silent damage in this app. One real
11-contact run produced three different markdown shapes and damaged 4 of the
11 notes, one down to a bare 137-byte header.

Observed shapes, all from the same agent:

```
### OUTPUT 1: VOICEMAIL SCRIPT        **OUTPUT 1: VOICEMAIL SCRIPT**
**Objection:** "..."                  Objection: "..."
* **Response 1:** "..."               Response 1: "..."
```

`_split_octave_sections` and `_format_objections_html` now accept every shape
above. `tests/fixtures/` holds the real Octave output that broke each one, so a
new shape gets a fixture, not a patch. **If a note looks short, run the raw
script through `services.formatting._split_octave_sections` before suspecting
Octave.** A section that comes back `""` is a parser gap, not an agent failure.

**10. The prep note is bullets, not prose, and that is deliberate.** Theresa
read the written-out scripts word for word and sounded like she was reading.
`OUTPUT 0: CALL INTEL` is the only prose section, because she reads it before
dialling. Everything below it is bullets capped at 10 words. The cap lives in
the agent prompt, and the training examples demonstrate it. **Examples override
instructions in practice**, so a prompt change that the examples contradict
will not take. Change both.

## Design decisions worth not re-litigating

- **The call start time stamps the plan. It does not schedule it.** The BDR
  picks a day and a start time. Both appear on the Route Plan, on every prep
  note, on the Slack sheet, and on Today's Climb. Neither one changes who is on
  the list, and neither reorders the time blocks. The blocks stay driven by the
  prospect's own time zone, because the strategy is to call every prospect at
  their local 10 to 11 AM.

- **Completion lives in the session file**, not HubSpot, because the `oracle_*`
  properties do not exist. The file sits on the Railway volume, so it survives a
  restart.
- **The outcome is recorded before the HubSpot write.** A HubSpot outage must not
  make the BDR lose their place in the list.
- **A failed `do_not_call` is its own UI state.** It un-ticks the card and shows a
  distinct message. It deliberately does not share a path with a failed note,
  because a routine "saved anyway" notice is what people learn to click past.
- **Railway, not Vercel.** `sessions/` is local disk and `/generate` holds one SSE
  response open across many 30 to 60 second Octave calls.
